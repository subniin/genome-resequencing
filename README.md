# genome-resequencing

짧은 read(short read)만으로 유전체를 복원하는 **De novo 조립**을 다룬 프로젝트입니다. 설계 프로젝트 조건(`알고리즘응용_설계.pdf` 60~64쪽)에 맞춰 실험했고, 발표 구성(Introduction, Benchmark, Algorithm, Result, Future work)에 따라 정리합니다.

## 1. Introduction

### 1.1 문제 정의

길이 L인 short read M개가 주어졌을 때, 그 read가 나온 길이 N의 원본 서열을 복원합니다 (PDF 60쪽). 이 저장소는 다음 선택을 했습니다.

- **de novo**: 조립기는 read만 입력으로 받는다. reference는 평가 단계에서만 읽는다.
- **single-end**, 정방향 read만 사용한다. paired-end와 역상보 가닥은 future work다.
- SNP가 있는 sample genome을 복원하고, 정답 SNP를 얼마나 찾았는지 평가한다.

### 1.2 조건과 실험 범위

| 항목 | PDF 조건 (61쪽) | 이 저장소 실험 |
|---|---|---|
| N (유전체 길이) | 최대 3×10^9 | 10^5 ~ 10^8 (실측 최대 N=10^8) |
| M (read 개수) | 약 2×10^7 ~ 2×10^8 | 2×10^4 ~ 2×10^7 (실측). 2×10^8은 외삽 |
| L (read 길이) | 약 32 ~ 100 | 32 / 50 / 75 / 100 |
| D (read당 mismatch 수) | 허용치로 정함 | D = 2 (기본), 0 ~ 3 비교 |
| repeat | 있을 수 있음 | 단계 6에서 20개 삽입 |
| read 형태 | single-end 또는 paired-end | single-end |
| 방식 | de novo 또는 reference | de novo |

기본 설정은 N = 10^5, L = 50, coverage 10, SNP 0.1%, o = ⌈L/2⌉ = 25, D = 2입니다. 한 번에 한 변수만 바꿉니다.

### 1.3 데이터 생성

- **reference**: 모든 16-mer가 서로 다른 ACGT 랜덤 서열을 만든다. 한 염기씩 붙이면서 새로 생긴 16-mer가 이미 나왔으면 다른 염기를 고르고, 막히면 한 칸 되돌아간다. 4^16 ≈ 4.3×10^9 공간에서 N=10^8까지 가능하다. 난수는 `mt19937_64`에 고정 seed를 쓴다.
- **repeat**: 단계 6에서만 쓴다. 길이 R 구간을 고른 뒤 |s−t| ≥ R인 다른 위치에 덮어써 20개 복사본을 만든다.
- **sample**: reference에 SNP를 무작위 위치에 치환으로 넣는다 (SNP 0.1%가 기본).
- **read**: sample에서 길이 L인 구간을 시작 위치 균등 분포로 뽑는다. M = round(N·coverage/L). 단계 5에서는 염기마다 확률 `err`로 다른 염기로 바꾼다.

### 1.4 입출력 형식

- 입력 read 파일: 한 줄에 read 하나. 빈 줄과 CR은 무시하고, 길이가 다르면 줄 번호와 함께 중단한다.
- 출력: contig FASTA (`>contig_0`, ...).
- 정답 SNP: `pos<TAB>ref<TAB>alt` TSV, 0-based.
- 평가 출력: accuracy, snp_recall, snp_precision, n_contigs, n50, covered_frac, misassemblies, unaligned_contigs, unaligned_bases_frac. accuracy는 reference에 정렬된 contig의 염기만으로 계산하고, 정렬되지 않은 contig의 염기 비율은 unaligned_bases_frac으로 따로 낸다. 실험 CSV에는 평가에 쓴 anchor 길이 `k_eval`도 기록한다.

## 2. Benchmark

비교 대상은 **Greedy Overlap**입니다. 모든 read 쌍의 최대 겹침을 한 번씩 계산하고, 겹침이 긴 순서대로 연결한다. 양쪽 끝이 비어 있고 사이클을 만들지 않을 때만 잇는다(union-find). 구현이 단순해서 정확성 기준선으로 쓰기 좋지만, 쌍 비교가 M²에 비례해 큰 M에서는 돌릴 수 없다. 그래서 실측은 M ≤ 3.1×10^4 범위에서만 했다.

## 3. Algorithm

### 3.1 SSAKE 계열 seed-and-extend

read 하나를 seed로 잡고, 그 3' 끝과 겹치는 read를 찾아 반복해서 붙입니다. 더 붙일 read가 없으면 contig를 닫고 남은 read로 새 seed를 시작합니다. 3' 연장 후에 5' 연장을 같은 방식으로 한다. 한쪽만 연장하면 seed 왼쪽 read가 별도 contig로 남아 조각난다.

### 3.2 이 구현의 자료구조

- **2-bit 압축 read** (`PackedReads`): 염기 하나를 2비트로 저장한다. read 하나는 2L 비트이고 64비트 단어 단위로 올림하므로 L=50이면 100비트가 2단어, 즉 16바이트다. 문자열(염기당 1바이트, 50바이트) 대비 약 1/3이다.
- **정렬 배열 색인**: read마다 key를 만든다. key는 앞 kk = min(o, 32)염기(prefix) 또는 뒤 kk염기(suffix)다. (key, read id) 쌍을 key 순으로 정렬해 두 배열(keys, ids)로 둔다. 조회는 `equal_range`로 한다.
- **연장 조건**: contig 끝 k염기(k는 o에서 L−1까지 큰 값부터)에 대응하는 key로 후보를 찾고, 겹침 전체 길이 k에 대해 mismatch ≤ D를 확인한다. kk가 32로 잘리므로 o > 32 (L=75, 100)에서도 key는 32염기만 쓰고, 검증은 겹침 전체로 한다.
- **중복 제거**: 같은 read는 첫 번째 사본만 남긴다. 정렬 후 같은 내용끼리 묶어 id가 가장 작은 것만 남긴다. 정렬용 `order` 배열이 read당 4바이트의 임시 메모리다.
- **다수결 연장** (`--vote 1`, 기본 꺼짐): 겹치는 모든 unused read가 다음 염기에 한 표씩 던진다. 각 read는 자기 겹침 길이에 맞는 위치의 염기를 낸다. 같은 위치 표가 2개 이상이고 최다 염기 비율이 2/3 이상이면 한 염기 붙인다. 표가 하나 남으면 충돌이 없으므로 그 염기를 붙인다. 표를 낸 뒤 탈락한 read와 끝까지 따라간 read는 사용 처리한다.

### 3.3 복잡도

M = read 수, L = read 길이, o = 최소 겹침.

| 도구 | 시간 | 공간 |
|---|---|---|
| SSAKE (이 구현) | O(M log M + M·(L−o)·(log M + L)) | O(M·⌈2L/64⌉·8 + 24M) bytes 상주, 색인 구축 중 임시 +16M |
| Greedy Overlap | O(M²·L²) (쌍마다 겹침 계산) | O(M²) (후보 쌍) |

read당 바이트 계산 (L=50, 코드에서 읽은 값):

| 항목 | 바이트/read | 비고 |
|---|---|---|
| `data` (2-bit read) | 16 (용량 여유로 최대 32) | 2 단어. `vector`가 `resize`로 자라므로 용량이 크기보다 클 수 있다 |
| prefix 색인 | 12 | key 8 + id 4 |
| suffix 색인 | 12 | key 8 + id 4 |
| 색인 구축 임시 `pairs` | 16 (구축 중에만) | `pair<uint64,uint32>`가 16바이트로 패딩된다. 색인마다 만들고 버린다 |
| 중복 제거 `order` | 4 (임시) | 색인 구축 전에 해제된다 |

suffix 색인을 만드는 순간이 정점이다: 16 + 12 (prefix) + 16 (pairs) + 12 (새 색인) = 56 B/read(용량 여유 없을 때). 실측은 M=2×10^6에서 약 46 B, M=2×10^7에서 약 52 B다 (4.3절). 합산이 실측보다 약 8% 크다. 이 차이의 원인은 확인하지 않았다(가설: 20ms 간격 샘플링이 정점을 놓치거나, 중복 제거로 M이 줄었다). `data` 용량 여유가 있으면 합산은 더 커져 실측과 더 멀어지므로, 이 표는 실측을 정확히 설명하지 못하는 근사로 본다.

### 3.4 다수결 연장 (단계 5 결과에 따른 추가)

단계 5(4.7절)에서 SSAKE의 오류율 0.01, D=2 결과(accuracy 0.981, precision 0.016)가 실행 조건(accuracy < 0.999 또는 precision < 0.9)을 만족해 다수결 연장을 실행했다. 이 조건은 accuracy를 정렬 안 된 contig까지 포함해 계산하던 때 정한 것이다 (4.7절 판정 참고). 결과는 4.7절 표의 `ssake_vote` 행에 있다. 오류율 0.01에서 accuracy는 0.9807에서 0.9822로, precision은 0.0164에서 0.0183으로 거의 변하지 않았다. 다수결이 오류 문제를 해결하지 못했다. 기본 설정은 다수결을 끈 상태이며 단계 0~4, 6의 결과는 다수결 없이 얻은 것이다.

**왜 효과가 없는가 (실측).** 오류율 0.01, D=2, N=10^5 데이터에서 `ssake.cpp`에 카운터만 넣은 사본(저장소에는 없음)으로 `--vote 1`을 돌려 센 값이다. 이전 README의 "겹치는 read가 평균 5~6개뿐"이라는 설명은 이 측정으로 지지되지 않는다 (3' 연장 기준).

- 3' 연장이 끝난 4705번 중 후보가 없어서 끝난 것이 4557번, 첫 염기(t=0)부터 2/3 충돌이어서 끝난 것이 148번이다. 연장 도중 충돌로 멈춘 투표 단계는 302번이다. 충돌은 드물고, 대부분 후보를 못 찾아 끝난다.
- 후보를 못 찾는 주된 이유로 보이는 것은 key가 앞 25염기의 정확 일치라는 점이다. 앞 25염기에 오류가 있는 read는 색인에서 찾아지지 않는다. 그 비율은 1 − 0.99^25 ≈ 22%다 (계산).
- 투표가 시작된 3063번 중 후보가 1~3개뿐인 경우가 2196번(72%)이다. 표가 하나 남아 그 염기를 그대로 붙인 단계가 21591번이다. 단일 후보 수락은 다수결이 아닌 방식과 같게 동작한다.
- 투표는 앞으로 붙일 염기만 정한다. 이미 contig에 들어간 염기(seed의 오류 포함)는 고치지 않는다 (코드 구조).
- t=0에서 충돌이 나면 다수결은 연장을 멈추지만 다수결이 아닌 방식은 첫 후보로 계속 간다. 그 결과 N50이 56(다수결 없음)에서 50(다수결)으로 줄었다 (`results/step5.csv`).

**precision 가설도 확인했다.** CSV의 precision 0.0164와 recall 1.000에서 호출 수는 약 100/0.0164 ≈ 6100개이고, 그중 정답은 약 100개다. 나머지는 거짓 호출이며, 리뷰어가 따로 센 바로는 contig 안의 sample과 다른 염기(오류 염기)가 약 5700개였다 (리뷰어 실측). 즉 contig에 남은 오류 염기가 SNP 호출로 집계된다는 설명이 맞다.

### 3.5 알려진 한계

- 탐욕 방식이라 repeat에서 연장이 멈추거나 잘못 이어질 수 있다 (단계 6에서 확인).
- read 오류가 있으면 contig에 오류 염기가 남고, 그 염기가 SNP로 잘못 호출된다 (단계 5에서 precision이 크게 떨어짐).
- 최소 겹침 o가 너무 크면 연결 가능한 쌍이 줄어 contig가 늘어난다 (단계 4 o=35).

### 4.3 단계 1: M에 따른 시간·메모리 (L 50, coverage 10, SNP 0.1%)

N = M·L/coverage로 두었다. M을 2×10^4 ~ 2×10^7로 올리면 N은 10^5 ~ 10^8이다.

| M | N | SSAKE 시간 (s) | SSAKE 메모리 (MB) | contig | N50 | recall | misassembly | 평가 k |
|---|---|---|---|---|---|---|---|---|
| 2×10^4 | 10^5 | 0.059 | 4.3 | 135 | 1266 | 1.000 | 0 | 24 |
| 2×10^5 | 10^6 | 0.282 | 12.8 | 1213 | 1350 | 1.000 | 0 | 24 |
| 2×10^6 | 10^7 | 3.972 | 88.3 | 12189 | 1349 | 1.000 | 0 | 24 |
| **2×10^7** | **10^8** | **73.45** | **986.9** | 122100 | 1335 | 0.99989 | 0 | 28 |

- 실측 최대(M=2×10^7, N=10^8)에서 SSAKE 피크 메모리는 987 MB로 목표 2.0GB 이하를 만족했다.
- read 1개당 메모리는 M=2×10^6에서 약 46 B, M=2×10^7에서 약 52 B다.
- Greedy Overlap은 M=2×10^4에서만 돌렸다: 42.581초, 11.7 MB. 같은 입력에서 SSAKE는 0.059초라 약 720배 차이다. SSAKE 시간이 0.03~0.12초로 흔들리므로(4.1절) 배율은 약 350~1400배 범위로 읽어야 한다. Greedy는 쌍 비교가 M²에 비례하므로 M=2×10^7은 실행하지 않았다.

**평가 k를 N에 따라 정했다.** 평가 anchor 길이는 N ≤ 10^7이면 k=24, N > 10^7이면 k=28이다 (`scripts/run_experiments.py`의 `k_eval_for`, CSV의 `k_eval` 열). 이전에는 모든 N에 k=24를 썼고, N=10^8에서 misassembly가 2로 나왔다. 그 contig는 길이 2035인 contig 하나이고 sample의 정확한 부분 문자열이다(리뷰어 확인). 같은 contig를 `evaluate`로 직접 다시 돌린 결과(CSV에 없는 수동 실행)는 다음과 같다.

| N | k=20 misassembly | k=24 | k=28 |
|---|---|---|---|
| 10^7 | 0 | 0 | 0 |
| 10^8 | 29 | 2 | 0 |

k=28에서는 N=10^8 misassembly가 0이고, 대신 정렬 안 된 contig가 7개(염기 비율 0.000004), recall은 0.99989(k=24에서는 0.99993)다. 즉 N=10^8의 misassembly 2는 평가기의 오탐이다. 원인으로 보는 것은 SNP나 오류가 낀 contig k-mer가 reference의 다른 고유 k-mer와 우연히 같아지는 것이다. 대략 계산하면 SNP를 낀 24-mer는 약 2.4×10^6개, 이것이 1×10^8개 위치 중 하나와 우연히 같을 확률은 개당 약 1×10^8/4^24 ≈ 3.6×10^-7이라 기대값이 약 0.9다. 관측된 2와 같은 자릿수이지만, 이 계산은 가설을 지지하는 추정일 뿐 직접 센 값이 아니다.

**M=2×10^8 외삽 (실측 아님).** 시간은 M이 10배(2×10^6 → 2×10^7)일 때 3.972초 → 73.45초로 18.5배 늘었다. 선형(10배)이면 73.45초 × 10 ≈ 12분, 이 18.5배가 한 번 더 이어지면 약 23분이다. 어느 쪽도 외삽이고, 직전 구간의 배율(2×10^5 → 2×10^6)은 14.1배라서 배율이 커지는 추세다. 메모리는 read당 바이트가 46 → 52 B로 늘고 있어 52 B × 2×10^8 ≈ 10.4 GB는 하한에 가깝다. 16GB 램에서 이론상 들어가지만 OS와 read 파일 버퍼를 빼면 여유가 작다.

|---|---|---|---|---|---|

SNP 비율이 1%까지 올라도 recall은 1.000으로 같다. 이 설계에서 read는 sample에서 뽑으므로 SNP가 read에 그대로 들어 있다. 그래서 SNP는 조립을 방해하지 않고 평가에서만 기록된다.

### 4.6 단계 4: read 길이 L과 최소 겹침 o

| L | o | M | SSAKE contig | SSAKE N50 | SSAKE 시간 (s) | Greedy 시간 (s) | recall (둘 다) |
|---|---|---|---|---|---|---|---|
| 32 | 16 | 31250 | 194 | 806 | 0.058 | 57.76 | 1.000 |
| 50 | 25 | 20000 | 135 | 1266 | 0.056 | 43.43 | 1.000 |
| 75 | 38 | 13333 | 85 | 2013 | 0.033 | 30.31 | 1.000 |
| 100 | 50 | 10000 | 76 | 1976 | 0.033 | 24.79 | 1.000 |

L=100(o=50)은 o가 32를 넘는 경로다. key는 32염기만 쓰고 겹침 전체를 검증했는데도 recall 1.000, misassembly 0으로 정상 조립되었다.

L=50에서 o만 바꾼 결과:

| o | SSAKE contig | SSAKE N50 | Greedy contig |
|---|---|---|---|
| 20 | 42 | 3732 | 42 |
| 25 | 135 | 1266 | 135 |
| 35 | 922 | 164 | 922 |

o를 크게 잡을수록 contig 수가 늘었다. o=35에서 contig 922개는 o가 L에 가까워져 연결 가능한 쌍이 줄기 때문으로 보인다(가설). 확인하지 않았다. 모든 설정에서 misassembly는 0이었다.

### 4.7 단계 5: read 오류와 mismatch 허용치 D (N 10^5, L 50, coverage 10)

오류 실험은 D = 2로 고정하고 오류율을 바꾼 것과, 오류율 0.01에서 D를 바꾼 것 두 가지다. accuracy는 정렬된 contig의 염기만으로 계산한 값이고, `unal`은 정렬 안 된 contig 염기 비율(`unaligned_bases_frac`)이다.

| 오류율 | SSAKE accuracy | precision | unal | recall | contig | ssake_vote accuracy | precision | unal | contig | Greedy accuracy | precision | unal | recall | contig |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 0 | 1.000000 | 1.000 | 0.000 | 1.000 | 135 | 1.000000 | 1.000 | 0.000 | 135 | 1.000000 | 1.000 | 0.000 | 1.000 | 135 |
| 0.005 | 0.986816 | 0.032 | 0.031 | 0.990 | 2859 | 0.987753 | 0.036 | 0.032 | 2641 | 0.991581 | 0.078 | 0.010 | 0.990 | 870 |
| 0.01 | 0.980724 | 0.016 | 0.065 | 1.000 | 4844 | 0.982181 | 0.018 | 0.068 | 4705 | 0.982638 | 0.032 | 0.038 | 1.000 | 1625 |
| 0.02 | 0.972896 | 0.009 | 0.164 | 0.990 | 8502 | 0.974786 | 0.009 | 0.163 | 8652 | 0.968934 | 0.013 | 0.134 | 0.970 | 3656 |

`ssake_vote`는 `--vote 1`로 같은 SSAKE를 돌린 결과다 (recall은 0.005에서 1.000, 0.02에서 0.990). 다수결은 contig 수를 조금 줄이고(0.01에서 4844 -> 4705) accuracy를 0.0015, precision을 0.002 올리는 데 그쳤다.

**accuracy 정의가 바뀌었다.** 이전 결과(accuracy 0.917, Greedy 0.945 등)는 정렬되지 않은 contig를 전부 불일치로 세어 분모에 넣었다. 그 값은 조립 품질보다 평가기의 k에 좌우됐다: 같은 contig를 오류율 0.01에서 평가하면 k=14에서 0.979, k=20에서 0.960, k=24에서 0.917, k=32에서 0.740이었다 (리뷰어 측정, CSV에 없음). 지금은 정렬된 contig 염기만으로 accuracy를 내고 정렬 안 된 염기 비율을 따로 보고한다. 새 수치에서 SSAKE와 Greedy의 accuracy 차이는 오류율 0.01에서 0.9807 대 0.9826으로 0.002뿐이고, 이전 값은 새 값에 정렬된 비율을 곱한 것과 같다 (SSAKE 0.9807 × (1 − 0.065) ≈ 0.917, Greedy 0.9826 × (1 − 0.038) ≈ 0.945, 계산). 즉 이전 차이는 정렬 안 된 contig 비율(SSAKE 0.065, Greedy 0.038)에서 온 것이다.

오류율 0.01에서 D를 바꾼 결과:

| D | SSAKE accuracy | unal | recall | contig | Greedy accuracy | unal | recall | contig |
|---|---|---|---|---|---|---|---|---|
| 0 | 0.979759 | 0.051 | 0.990 | 7443 | 0.979638 | 0.051 | 1.000 | 7487 |
| 1 | 0.979851 | 0.060 | 1.000 | 5474 | 0.978755 | 0.064 | 1.000 | 3370 |
| 2 | 0.980724 | 0.065 | 1.000 | 4844 | 0.982638 | 0.038 | 1.000 | 1625 |
| 3 | 0.980979 | 0.065 | 1.000 | 4753 | 0.986138 | 0.016 | 1.000 | 1135 |

D가 커져도 SSAKE accuracy는 0.9798 ~ 0.9810으로 거의 변하지 않고, Greedy는 0.9796에서 0.9861로 오른다. Greedy는 D가 커질수록 정렬 안 된 비율이 0.051에서 0.016으로 줄고 contig 수가 7487에서 1135로 준다.

판정: 오류율 0.01, D=2에서 SSAKE accuracy는 0.981로 0.999보다 낮고, SNP precision은 0.016으로 0.9보다 낮다. Task 8의 실행 조건(accuracy < 0.999 또는 precision < 0.9)은 accuracy를 정렬 안 된 contig까지 분모에 넣은 값(당시 0.917)으로 판정했다. 그 값은 위에서 보인 대로 평가기 k에 오염되어 있었다. 정렬된 염기만으로 다시 계산한 지금도 accuracy 0.981 < 0.999, precision 0.016 < 0.9라서 조건은 그대로 만족한다. 다만 accuracy가 아닌 precision이 판정을 이끈다. precision이 낮은 이유는 contig에 남은 시퀀싱 오류 염기가 reference와 다른 염기로 집계되어 정답 없는 SNP로 호출되기 때문이며, 3.4절에서 호출 수를 세어 이 설명을 확인했다. Task 8과 다수결 코드는 그대로 둔다.

### 4.8 단계 6: repeat (N 10^5, L 50, 반복 20개)

| repeat 길이 | SSAKE misassembly | SSAKE recall | SSAKE precision | SSAKE accuracy | Greedy misassembly | Greedy recall | Greedy precision |
|---|---|---|---|---|---|---|---|
| 25 | 0 | 1.000 | 1.000 | 1.000000 | 0 | 1.000 | 1.000 |
| 50 | 7 | 0.980 | 0.560 | 0.998954 | 21 | 1.000 | 0.952 |
| 100 | 11 | 0.980 | 0.551 | 0.993423 | 15 | 0.970 | 0.858 |
| 200 | 10 | 0.990 | 0.723 | 0.984358 | 13 | 1.000 | 0.980 |

repeat 길이가 read 길이(50)보다 짧은 25에서는 오조립이 없었다. 길이가 50 이상이 되면 misassembly가 생겼다. 200에서 SSAKE의 covered_frac은 0.963, unaligned는 1이었다. 반복이 있으면 precision이 크게 떨어진다. 이 단계의 오조립 contig를 리뷰어가 하나씩 sample과 대조한 결과 모두 sample에 없는 서열이었다 (별도 검사, 스크립트는 저장소에 없음). 따라서 repeat에서 잘못 이어진 contig가 sample에 없는 염기를 만들고, 그것이 SNP 호출을 오염시킨다는 설명은 확인된 결과다.

### 4.9 평가 수정 이력

초기 평가 도구는 문자열 k-mer 맵을 썼고, anchor k=14를 기본으로 했다. 이전 README는 N=10^7(L=30, SNP 0.5%, o=15)에서 k=14와 24를 비교한 표를 실었으나, 그 수치(misassembly 8786 대 11 등)는 어떤 CSV나 스크립트로도 재현되지 않아 폐기했다. 대신 `scripts/check_eval_k.py`가 같은 설정에서 SSAKE contig 한 벌(19402개)을 만들어 k만 바꿔 평가하고 `results/eval_k_check.csv`에 쓴다.

| k | accuracy | SNP recall | SNP precision | misassembly | unaligned contig | unal 염기 비율 |
|---|---|---|---|---|---|---|
| 14 | 0.999648 | 0.910420 | 0.960886 | 8157 | 0 | 0.000000 |
| 20 | 0.999864 | 0.999500 | 0.973223 | 42 | 17 | 0.000054 |
| 24 | 0.999863 | 0.999140 | 0.973214 | 42 | 43 | 0.000145 |
| 28 | 0.999858 | 0.998540 | 0.973198 | 42 | 84 | 0.000306 |

k=14에서는 misassembly가 8157, recall이 0.910으로 나오고, k ≥ 20에서는 42, 0.999 이상으로 안정된다. 같은 contig인데 평가 k만 바뀐 결과이므로 k=14의 수치는 평가기의 문제다. 큰 k는 정렬 안 되는 contig를 늘린다 (17 → 84개).

가짜 anchor가 생기는 경로는 다음과 같다. 평가기는 reference에서 두 번 이상 나오는 k-mer를 버리므로(`evaluate.cpp`) 반복 k-mer가 anchor를 만들지는 않는다. 가짜 anchor는 SNP나 오류를 품은 contig k-mer가 reference의 다른 곳에 있는 고유 k-mer와 우연히 같을 때 생긴다. 이 경로는 `tests/test_evaluate.cpp`의 합성 사례(SNP k-mer를 먼 위치에 심음)로 재현된다. k=14에서 4^14 ≈ 2.7×10^8이 N=10^7과 같은 자릿수라 우연한 일치가 흔하다는 설명은 계산에 기반한 추정이며, 가짜 anchor를 직접 세지는 않았다. 평가는 k=24(N > 10^7이면 28)로 고정해 단계 0~6을 다시 실행했다. 이전 README의 수치(N=10^4)는 이 실험 설계와 다르므로 사용하지 않는다.

### 4.10 구현에서 정한 것 (원 논문과 다른 점)

- 중복 read는 두 조립기 모두 입력 단계에서 첫 번째 사본만 남긴다.
- SSAKE 연장 후보가 여러 개면 입력 순서상 첫 번째를 쓴다. 다수결(`--vote 1`)은 3.4절에서 설명한 대로 추가되어 있고 기본은 꺼짐이다.
- accuracy는 정렬된 contig의 염기 중 sample과 일치하는 비율이다. 정렬되지 않은 contig는 accuracy 분모에서 빼고 `unaligned_bases_frac`로 따로 보고한다.
- 평가는 reference 고유 k-mer(k=24, N > 10^7이면 28) anchor로 대각선 구간을 잡고 꼬리까지 채점한다. reference 위치는 64비트라 N > 2^31도 다룬다. 색인은 reference 염기당 16바이트다.

## 5. Future work

### 장점과 단점

- **장점**: 메모리가 read당 약 50바이트로 작고, M=2×10^7을 단일 PC에서 1GB 이하(987 MB)로 돌렸다. 정확한 read에서는 recall 1.000을 보였다.
- **단점**: 오류 read에 약하다 (단계 5: 오류율 0.01에서 precision 0.016). repeat 길이가 read 길이 이상이면 오조립이 생긴다 (단계 6). 역상보와 paired-end를 쓰지 않아 정보가 부족하다.

### 개선 방안

- paired-end와 역상보 가닥을 입력에 추가해 repeat 연결을 돕는다.
- de Bruijn graph 기반 조립과 비교한다. 오류 k-mer를 빈도로 걸러내는 방식이 오류 read에 효과적일 것으로 기대하나(가설) 아직 구현하지 않았다.
- BWT 기반 색인으로 read 저장과 조회 메모리를 더 줄인다.
- 색인을 디스크에 두어 M=2×10^8 실측을 가능하게 한다.
